## What this FIXME asks for
When the formal model workload generator is configured for disaggregated storage mode, it forcibly sets `_spec.prepared_transaction = 0`, preventing the generator from ever producing workloads containing prepared transactions. This means the formal model provides no verification of prepared-transaction correctness (prepare, commit, or rollback) under disaggregated storage. The FIXME asks for prepared transaction support to be implemented in disaggregated storage first, then this constraint to be lifted so the model can test it.

## Importance: HIGH
**Reasoning**: Prepared transactions are a critical correctness feature used by MongoDB for multi-document transactions. The formal model (test/model) is one of the strongest correctness verification tools in WiredTiger's test suite. With this constraint in place, any bug in prepared-transaction handling under disaggregated storage would not be caught by the formal model tests. Given that disaggregated storage has a complex reconciliation and visibility path, prepared-transaction edge cases (e.g., prepare visibility, rollback after prepare, crash during prepare commit) are exactly the scenarios where bugs are most likely to hide.

## Test Coverage: UNCOVERED
**Relevant tests**: test/model disagg workload tests (via WT-15071), but only without prepared transactions
**Gap**: No formal model test exercises prepared transactions in disaggregated storage mode. Python suite tests with the disagg hook may cover some prepared transaction paths but without the exhaustive state-space exploration that test/model provides.
