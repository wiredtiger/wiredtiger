## What this FIXME asks for
The on-disk page header (`WT_PAGE_HEADER`) currently has a fixed 28-byte size with no extensibility mechanism. The `reserved` byte at offset 26 was claimed from an unused field to hold this reserved slot. The full ticket asks that this byte be repurposed as `extra_header_length`, encoding how many bytes beyond the base 28-byte header are present, enabling future additions to the page header in a backward-compatible way. All existing code that assumes a fixed header size via `sizeof` would need updating, and validation on read must be added.

## Importance: MEDIUM
**Reasoning**: This is a forward-compatibility concern for the on-disk format. Until resolved, adding fields to the page header requires a coordinated flag-day change and careful upgrade/downgrade planning. The `reserved` byte is already set to 0 on all existing deployments, so no current data is at risk — but future format evolution is constrained until this mechanism is implemented. The label `wt_data_format` signals it touches the durable storage format.

**Gap**: No test exists that validates the `reserved` byte is zero on read, that the extensibility mechanism correctly handles a non-zero `extra_header_length`, or that pages with an extended header can be read by older code. The ticket explicitly lists adding a test as a deliverable.
