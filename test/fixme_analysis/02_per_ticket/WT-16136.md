## What this FIXME asks for
When iterating history-store entries via the version cursor, the code cannot reliably distinguish whether a `stop_ts == WT_TS_MAX` (no tombstone) entry's `durable_stop_ts` was set by a tombstone delete or inherited from the preceding full-value write. The current workaround conservatively returns the value whenever `durable_start_ts <= start_timestamp`, which may cause the version cursor to include entries it should logically exclude. The FIXME asks to implement proper disambiguation so the version cursor can apply the correct stop-timestamp filtering for history-store entries.

## Importance: MEDIUM
**Reasoning**: Incorrect stop-timestamp attribution can cause the version cursor to return stale or logically-deleted key versions that should be filtered out. This affects correctness of point-in-time reads that rely on the version cursor (e.g., disaggregated storage follower reads, replication, and diagnostic tooling). However, the conservative "always return" fallback avoids data loss; the risk is extra rows being visible rather than missing rows.

## Test Coverage: PARTIAL
**Relevant tests**: test/suite/test_version_cursor*.py (if present); version cursor tests in test/suite/

Existing version cursor tests likely exercise the general case but not this specific boundary condition with `stop_ts == WT_TS_MAX` combined with a durable stop timestamp set by a tombstone.
