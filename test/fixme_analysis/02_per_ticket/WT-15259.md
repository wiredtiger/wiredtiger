## What this FIXME asks for
Both `bt_sync_obsolete.c` (checkpoint-cleanup sweep) and `conn_compact.c` (background compaction) independently implement the same pattern: open a metadata cursor with `WT_ISO_READ_UNCOMMITTED`, do a `search_near`, then loop calling `cursor->next` under the same isolation to advance past the target URI. The FIXMEs ask for this duplicated forward-traversal pattern to be extracted into a shared internal API, which would then allow both callers to be simplified and would consolidate the isolation-level logic in one place. The ticket was originally filed because this `read_uncommitted` isolation pattern was linked to a crash (zero btree_id passed to history-store lookup) introduced by the disagg merge.

## Importance: MEDIUM
**Reasoning**: The ticket status is Blocked (as of 2026-04-14 a PR was merged, reducing urgency), and the code pattern is duplicated rather than incorrect in the current state. However, duplicated metadata-traversal with manually managed `read_uncommitted` isolation is a latent correctness hazard: any future change to one copy that is not mirrored in the other could silently reintroduce isolation bugs. The original crash was a P3 with real production impact.

## Test Coverage: PARTIAL
**Relevant tests**: Background-compact tests in `test/suite/` (e.g. `test_background_compact*.py`) exercise `conn_compact.c`; checkpoint-cleanup sweep is exercised by the broader checkpoint stress tests.
**Gap**: There is no test that specifically validates the isolation level or the loop-termination behavior of the metadata forward-traversal, so a regression in the shared API once it is created would not be caught by targeted unit tests.
