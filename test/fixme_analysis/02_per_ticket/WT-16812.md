## What this FIXME asks for
`__wt_layered_table_truncate_detect_write_conflict` is currently called from two places in the layered cursor's put/remove paths (at the cursor layer) to detect conflicts between an incoming key write and any uncommitted truncate ranges in the follower truncate list. The FIXME asks whether this conflict check could instead be pushed below the cursor layer (e.g. into the page/BTree write path), which would decouple cursor write operations from the truncate list and simplify the cursor code. The broader ticket also calls for validating that all conflict patterns (truncate vs. insert, insert vs. truncate, overlapping truncates, timestamped variants) are correctly detected.

## Importance: HIGH
**Reasoning**: If write-conflict detection is incorrect or missing, follower fast truncate can silently allow conflicting operations to commit, producing data inconsistency between primary and standby. Wrong results under truncate+write concurrency is a correctness bug. The architectural question (where to call the check) is a secondary cleanup concern, but the validation of correctness is high priority.
