## What this FIXME asks for
TSAN (ThreadSanitizer) reports data races on `oldest_timestamp`, `has_oldest_timestamp`, `stable_timestamp`, and `has_stable_timestamp` fields. The race occurs because these fields are read from one thread (e.g., during transaction commit checking `__txn_check_if_stable_has_moved_ahead_commit_ts`) while being atomically written from another (e.g., `__wt_txn_global_set_timestamp`). Some accesses use acquire/release semantics (introduced as part of the disagg merge), while others use only relaxed atomics, creating mixed-ordering accesses on the same variables. The FIXME asks for a review of the correct synchronization model for these fields and for consistent application of the chosen memory order.

## Importance: HIGH
**Reasoning**: Data races on timestamp fields are real undefined behavior under C11/C++ memory model. A race on `stable_timestamp` during transaction commit could cause a transaction to be committed with a timestamp below stable, violating the monotonicity invariant and potentially causing correctness failures (incorrect read-your-writes, missed rollbacks). TSAN warnings on these fields have been explicitly suppressed rather than fixed, meaning real races may occur in production builds. This is a classification of actual Bug in Jira.
