## What this FIXME asks for
On disaggregated storage followers, `__disagg_metadata_table_init` opens the live dhandle for the shared metadata table even though followers should never access the live dhandle (per WT-15527). As a short-term workaround the live dhandle is immediately expired after creation. The FIXME asks to investigate whether followers need to create the shared metadata table at all, or whether this can be deferred until step-up, simplifying the follower initialization path and eliminating the need for the immediate dhandle expiration workaround.

## Importance: MEDIUM
**Reasoning**: The current workaround is functional but architecturally unsound — follower nodes open a live dhandle they should never use, relying on an immediate expiration to maintain the invariant that followers never access the live shared metadata. If the expiration step ever fails or is skipped (e.g., due to future refactoring), followers could inadvertently write to the shared metadata table, causing data corruption in the disaggregated storage cluster. The risk is mitigated by the existing guard code but the structural violation is a maintenance hazard.
