## What this FIXME asks for
The follower-mode (standby/disagg) fast-truncate design keeps an in-memory list of truncate ranges on a `WT_LAYERED_TABLE`. There are three deferred improvements: (1) find a more efficient way to look up the dhandle for a truncate entry without holding no global locks (currently an ASSERT_ALWAYS abort path is used); (2) sort the truncate list by start key or timestamp to speed up range searches rather than a linear scan; and (3) prevent the sweep server or follower mode from evicting a layered-table dhandle while truncate entries still reference it via the stored URI string, which is a potential use-after-free or dangling-dhandle hazard.

## Importance: HIGH
**Reasoning**: Issue (3) is a correctness/crash risk: if the sweep server evicts the layered-table dhandle while truncate-list entries still hold the URI and the code does an ASSERT_ALWAYS to re-acquire it, a removed dhandle can cause an assertion abort or silent wrong behavior during commit/rollback of a follower truncate. Issues (1) and (2) are performance concerns that could cause standby lag under heavy truncate workloads (the original motivation for the whole feature), which carries availability risk.

## Test Coverage: PARTIAL
**Relevant tests**: test/suite/test_layered_fast_truncate01.py, test/suite/test_layered_fast_truncate05.py, test/suite/test_truncate15.py
