## What this FIXME asks for
WT-14586 added crash recovery logic (`__metadata_clean_incomplete_table`) to detect and drop partially-created simple tables whose metadata is inconsistent after a crash. However, the implementation explicitly skips complex tables (multi-colgroup) and tiered tables. In `schema_drop.c` the cleanup path is only exercised when `table->is_simple` is true; in `txn_recover.c` recovery bails out early for any non-simple or tiered table. The FIXME asks for extending both paths to handle complex and tiered tables.

## Importance: HIGH
**Reasoning**: A crash during creation of a complex or tiered table leaves orphaned metadata entries and possibly orphaned files. On the next restart, the database opens with inconsistent metadata: the table entry exists but is incomplete, which can cause assertion failures, confusing errors, or data corruption if the table is subsequently accessed or if recovery attempts to replay operations against it. Because tiered tables are used in production Atlas deployments, this is a real operational risk.

## Test Coverage: UNCOVERED
**Relevant tests**: test/suite/test_schema_create*.py, test/suite/test_txn_recover*.py — existing tests cover the simple-table recovery path added by WT-14586
**Gap**: No tests exercise crash-during-creation for complex (multi-colgroup) tables or tiered tables, nor verify that recovery successfully cleans up the resulting inconsistent metadata. The skip paths in both files mean these scenarios are entirely unexercised.
