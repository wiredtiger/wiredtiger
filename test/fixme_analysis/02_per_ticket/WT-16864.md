## What this FIXME asks for
`__wti_block_disagg_decrease_size` is supposed to assert that `block_disagg->size >= size` before subtracting, to catch underflow in disaggregated block size accounting. This assertion was triggering in CI (causing an abort via `__wt_btree_decrease_size`), indicating a real accounting bug where the tracked size goes below zero. The FIXME disables the assert and instead silently clamps to zero, deferring proper fix until the underlying size accounting bug is resolved. The fix belongs to WT-16660 (bytes_total increment not protected by reconciliation panic boundary).

## Importance: HIGH
**Reasoning**: The suppressed assertion was guarding against a genuine size-accounting underflow in the disaggregated block manager. With the assert disabled, incorrect `bytes_total` accounting silently produces wrong storage size statistics and can mask further corruption. The bug was actively crashing model tests on multiple build variants (ASAN, stress, non-standalone), indicating it is not a rare edge case.

## Test Coverage: PARTIAL
**Relevant tests**: test/model (model-test-long-random-config-disagg), test/format (format-stress-test-disagg-follower-1/2, format-stress-test-disagg-leader-1)
**Gap**: The tests that exposed the bug are still running, but the guard assertion is disabled so they no longer catch size accounting underflows. Until the assert is re-enabled after the root-cause fix in WT-16660 (and WT-17034 for addr_pack inflation), regressions in disagg block size accounting will pass silently.
