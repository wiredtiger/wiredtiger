## What this FIXME asks for
In `__wt_schema_layered_truncate` (schema_truncate.c), when no stop cursor is provided, the function creates a local stop cursor positioned at the last key of the table and passes it to `__wt_layered_truncate`. This local cursor creation was added as a workaround so that the layered truncate path always has a valid stop cursor. The FIXME asks that this workaround be removed once the session truncate layer (`__wt_session_range_truncate` in session_api.c) is updated to create local cursors itself — mirroring the symmetrical handling it already does for the start cursor. Once session_api.c owns the cursor lifecycle uniformly, the workaround in schema_truncate.c becomes dead code and should be cleaned up.

## Importance: LOW
**Reasoning**: The current workaround is functionally correct — it ensures a valid stop cursor is always passed to the layered truncate path. The risk is primarily code-quality: the local cursor creation in schema_truncate.c creates a confusing split of responsibility between the schema and session layers. If the session layer is later updated to always provide stop cursors without updating this code, the workaround would create a double-close bug on the stop cursor. This is a maintenance hazard but not an immediate correctness issue.

## Test Coverage: PARTIAL
**Relevant tests**: test/suite/test_layered_fast_truncate01.py, test/suite/test_layered*.py
**Gap**: The no-stop-cursor path (where local_stop is created) is exercised by tests that call truncate without specifying a stop key. However, there is no test that specifically verifies the cursor lifecycle (open/close) in this workaround path, so a future double-close regression from the planned refactoring would not be caught by existing tests.
