## What this FIXME asks for
During checkpoint pickup (`__disagg_pick_up_checkpoint_meta`), when existing local metadata is compared against incoming shared metadata for an updated checkpoint:

1. **Line 378**: After detecting a checkpoint change, only the checkpoint field is compared; the rest of the metadata (key/value formats, compressor, encryptor, etc.) is not verified to be identical. If those fields diverged, the engine would silently accept inconsistent metadata.

2. **Line 404**: When a brand-new table entry is inserted from shared metadata, there is no check to ensure the new table's btree/file ID does not collide with an existing locally-assigned ID. A collision would corrupt the btree-ID-to-dhandle mapping and could cause I/O to the wrong file.

## Importance: HIGH
**Reasoning**: The btree ID conflict (line 404) is a potential data-corruption vector: if a new table arrives from shared metadata with a file ID already in use locally, two logical tables will share one physical file, leading to silent data corruption or crashes. The metadata consistency check (line 378) is a correctness gap — inconsistent metadata between cluster nodes would go undetected, potentially causing wrong query results or crashes when the engine uses divergent schema information.
