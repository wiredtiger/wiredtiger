## What this FIXME asks for
The `__create_tiered` function in `schema_create.c` inconsistently mixes `WT_RET`/`WT_RET_MSG` (which return immediately, bypassing cleanup) and `WT_ERR` (which jump to an `err:` label for cleanup). The FIXME was introduced when a `WT_RET_MSG` was added at the top of the function to block tiered creation on disagg connections. Because the function has an `err:` cleanup label and allocates resources later (e.g., scratch buffers via `__wt_scr_alloc`), all early-exit paths should use `WT_ERR`/`WT_ERR_MSG` rather than `WT_RET`/`WT_RET_MSG`, or the resources at risk of leaking on those paths need to be audited. Note: a Jira comment suggests this ticket should be closed as "Won't Do" when tiered storage is deprecated (tracked under SPM-4479).

## Importance: LOW
**Reasoning**: The current `WT_RET_MSG` at line 1320 fires before any heap allocations occur in the function, so it does not currently cause a resource leak. However, the mixed error-handling style is a maintenance hazard: future changes that reorder code or add allocations before line 1320 could silently introduce leaks. Since tiered storage is expected to be deprecated, the priority is low and this may never be fixed.

## Test Coverage: COVERED
**Relevant tests**: test/suite/test_tiered*.py (any test that tries to create a tiered table on a disagg connection will exercise the early-exit path)
**Gap**: There is no specific test that verifies resource cleanup (no leak) when `__create_tiered` returns early via `WT_RET_MSG`. Given the impending deprecation of tiered storage, adding such a test is likely not warranted.
