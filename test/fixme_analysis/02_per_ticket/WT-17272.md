## What this FIXME asks for
The test `test_truncate_write_conflict_2` exercises a scenario where a fast truncate on a follower should detect a write conflict against an uncommitted ingest update in the truncate range. The test is skipped because the underlying bug is not yet fixed: `search_near` in the truncate path does not invoke `__wt_txn_update_check`, so uncommitted ingest updates in the truncate range are silently missed. This is one of three write-conflict detection gaps identified in WT-17272, the other two being false negatives from `__wt_txn_visible`-only checks and missing conflict detection between two overlapping truncates with no ingest content.

## Importance: HIGH
**Reasoning**: This is a correctness bug in transactional conflict detection for fast truncate on follower nodes. If two concurrent transactions can both commit when one should roll back due to conflicting writes in a truncated range, the result is silent data inconsistency. Fast truncate is a performance-critical path, and correctness holes in its conflict detection could corrupt user data in a disaggregated storage deployment without any error being surfaced. The ticket is actively assigned (Will Korteland) and in the current sprint.
