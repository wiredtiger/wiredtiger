## What this FIXME asks for
During reconciliation of page deltas, the code uses `split_size` (rather than `page_size`) for both `space_avail` and `disk_img_buf_size`. This is described as a "temporary hack" to prevent buffer overflow when rewriting deltas. The Jira ticket asks for a more principled approach: a proper pessimistic buffer size estimation that accounts for the actual maximum size a reconciled delta can reach, instead of relying on the split size as a proxy. The current approach may over-allocate memory (wasting buffers) or could fail in edge cases where the delta size exceeds the split size.

## Importance: MEDIUM
**Reasoning**: This is a reconciliation memory management issue. Reconciliation is a core, frequently-called path. An incorrect buffer size estimate could cause either buffer overruns (leading to memory corruption or panics) or unnecessarily large allocations (memory waste per reconciliation). The "temporary hack" label acknowledges the solution is not robust. Since the Jira ticket has no description content and no comments, the exact risk bounds are unclear, but the code path is exercised on every checkpoint for delta-enabled pages.
