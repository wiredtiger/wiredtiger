## What this FIXME asks for
TSAN reports data races on `upd_start_ts` and `upd_durable_ts` fields of update records. At these two call sites in `__wt_txn_op_delete_commit` and `__wt_txn_op_set_timestamp`, the commit path assigns the transaction's commit/durable timestamp to an update record using `__wt_tsan_suppress_store_uint64` (a plain non-atomic write). Concurrently, reader threads use `__wt_atomic_load_uint64_relaxed` to read the same fields for visibility checks in `__wt_txn_upd_visible_type`. The FIXME marks the use of the TSAN suppression macro as a workaround. According to a comment in Jira, the fix is to use relaxed atomic stores instead of plain non-atomic stores, making both sides consistently use relaxed atomic accesses.

## Importance: HIGH
**Reasoning**: These are confirmed data races on live transaction update records between committing writers and concurrent readers. While Chenhao Qu notes the behavior is "by design" and relaxed atomics should suffice, any mix of plain writes and atomic reads constitutes undefined behavior under C11. The races affect the core read path (`__wt_txn_read_upd_list_internal`) and commit path, meaning incorrect visibility decisions (reading stale `upd_start_ts == WT_TS_NONE` after commit) could cause data to be invisible or visible at wrong timestamps. This is classified as Bug in Jira.

## Test Coverage: PARTIAL
**Relevant tests**: test/format (TSAN variant, WT-15784); races are actively suppressed via `__wt_tsan_suppress_store_uint64`
**Gap**: The TSAN suppressions mask these specific races, so CI does not detect regressions. No targeted concurrent test exercises the exact window where a reader checks `upd_start_ts` while a committer is writing it. The fix (converting to relaxed atomic stores) needs to be followed by removing the suppressions to allow TSAN to confirm the races are resolved.
