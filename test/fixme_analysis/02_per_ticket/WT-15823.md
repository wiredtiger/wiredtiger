## What this FIXME asks for
Under cache pressure WiredTiger may want to roll back a read-only transaction that is pinning the oldest timestamp and thus preventing cache eviction. In standalone builds this is already done. In MongoDB-embedded builds the `#ifndef WT_STANDALONE_BUILD` guard skips the rollback check entirely when `txn->mod_count == 0` and no operation timer has fired, because MongoDB's upper layers do not expect `WT_ROLLBACK` from a read-only transaction (tracked in SERVER-44870). The FIXME asks that this guard be removed once MongoDB can tolerate rollback on read-only transactions, enabling WT to reclaim cache more aggressively.

## Importance: MEDIUM
**Reasoning**: Cache pressure that cannot be relieved by rolling back long-running read transactions can cause eviction to stall, degrading throughput or causing out-of-memory conditions. The asymmetry between standalone and embedded behavior is a technical debt item that affects cache management correctness in production MongoDB deployments. Resolution is blocked on a cross-team dependency (SERVER-44870, currently Backlog).

## Test Coverage: PARTIAL
**Relevant tests**: The standalone code path (rollback allowed) is exercised by `#ifdef WT_STANDALONE_BUILD` builds. The embedded code path (rollback suppressed) is not specifically tested for cache-pressure scenarios; the behavior is implicitly validated by existing MongoDB integration tests that verify no unexpected `WT_ROLLBACK` is returned from read operations.
**Gap**: No targeted test verifies that removing this guard in a non-standalone build correctly handles cache pressure without breaking upper-layer callers.
