## What this FIXME asks for
When logging is enabled, a crash at the `CKPT_CRASH_BEFORE_METADATA_SYNC` crash point (after the checkpoint transaction commits and after the log flush, but before the metadata/turtle file is updated) produces a recoverable checkpoint from WiredTiger's perspective, because the log records are durable. However, `test/model` currently assumes that all crash points produce non-recoverable checkpoints. To prevent spurious test failures, the crash point was conditionally disabled when logging is enabled. The FIXME asks for `test/model` to be updated to understand and correctly verify recoverable checkpoint scenarios, at which point this workaround can be removed.

## Importance: HIGH
**Reasoning**: This is a correctness modeling bug: the workaround prevents a crash point from being exercised in the most realistic scenario (logging enabled), which is exactly the configuration MongoDB uses in production. The crash-after-log-flush/before-metadata-sync scenario is a real recovery path that could harbor bugs (e.g., incorrect transaction visibility after recovery, double-apply of log records). Until `test/model` correctly models recoverable checkpoints, this crash scenario remains untested under the formal model, and the workaround itself skews crash-point coverage.

## Test Coverage: PARTIAL
**Relevant tests**: test/model crash-point tests with logging disabled exercise the non-recoverable path; the recoverable path is currently blocked by the workaround.
**Gap**: No test/model scenario exercises the `CKPT_CRASH_BEFORE_METADATA_SYNC` crash point with logging enabled and verifies correct recovery. The workaround at checkpoint_txn.c:1504 must be removed and test/model updated to close this gap.
