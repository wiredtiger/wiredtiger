## What this FIXME asks for
During rollback-to-stable, the global `has_durable_timestamp` flag is updated by a plain non-atomic store (`txn_global->has_durable_timestamp = ...`), while the companion `durable_timestamp` field is correctly updated via `__wt_atomic_store_uint64_relaxed`. The FIXME asks for the boolean flag to also use an atomic write to ensure it is not subject to data races with concurrent readers on other threads. This is part of a broader effort (WT-16674/WT-16778) to make all accesses to the global timestamp fields properly atomic.

## Importance: HIGH
**Reasoning**: `txn_global->has_durable_timestamp` is a shared variable read by multiple threads without locks. A non-atomic write can result in a torn read or a stale cached value on another thread (a data race, which is undefined behavior in C). If a reader sees a stale `false` for `has_durable_timestamp` while `durable_timestamp` has already been atomically updated, it could make incorrect timestamp decisions. This is a concurrency correctness issue, albeit one that is unlikely to manifest in practice on platforms with coherent caches.

## Test Coverage: UNCOVERED
**Relevant tests**: none found for this specific atomicity invariant
**Gap**: Data races of this kind are only reliably detected by tools like TSAN (thread sanitizer). No targeted test exercises concurrent reads of `has_durable_timestamp` during RTS. The TSAN disagg format test added in WT-16715 may incidentally catch this, but there is no assertion or test that specifically validates atomic access to the flag.
