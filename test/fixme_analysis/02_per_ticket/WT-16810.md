## What this FIXME asks for
Three places in the layered cursor (`__clayered_get_current`, `__clayered_iterate_constituents`, `__clayered_search_near`) currently hard-code a guard that bypasses the ingest cursor entirely when the node is in leader mode. This was a workaround for WT-16695 that relies on the assumption that the ingest table is always empty after promotion. The FIXME notes this assumption will break when asynchronous step-up is supported, because ingest may remain non-empty for a window after promotion. The deferred work is to design and document proper role-aware cursor invariants and replace these guards with a correct implementation.

## Importance: MEDIUM
**Reasoning**: The current guards are functionally correct only under synchronous promotion (ingest drained before cursor operations resume). Once async step-up is implemented, skipping the ingest cursor will cause wrong query results — reads will miss data that is still in ingest but not yet flushed to stable. This is a correctness risk that is gated on a future feature, making it medium rather than high priority right now.

## Test Coverage: PARTIAL
**Relevant tests**: test/suite/test_layered31.py, test/suite/hook_disagg.py, test/suite/test_layered88.py
**Gap**: No tests exercise cursor reads on a layered table immediately after asynchronous leader promotion while ingest is non-empty, which is exactly the scenario the FIXME warns about. Tests that exist cover synchronous step-up or steady-state leader operation.
