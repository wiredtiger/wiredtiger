## What this FIXME asks for
During verification of a disaggregated btree, WiredTiger compares the checkpoint's recorded size (`ckpt->size`) against the accumulated block size computed during verify (`vs->total_block_size`). The check is currently disabled (`if (false)`) because `bytes_total` can be inflated by a silent accounting leak: when `__wti_block_disagg_addr_pack` fails after `plh_put` has already succeeded and `bytes_total` has been incremented, the increment is never rolled back. The FIXME asks for the underlying accounting bug to be fixed (move `bytes_total` increment past the panic boundary) and then for this verification check to be re-enabled.

## Importance: HIGH
**Reasoning**: This is a real correctness bug in the disagg block write accounting path. `bytes_total` can be permanently inflated by orphaned block writes, causing both a storage leak and an accounting divergence. The verification check was disabled specifically because of this bug — meaning a whole class of checkpoint size integrity checks is silently bypassed for disagg trees. The open PR was declined and WT-16864 (a related failing test) is still open, indicating active investigation. The FIXME removal is blocked on the feature branch merge.

## Test Coverage: UNCOVERED
**Relevant tests**: none that exercise the mismatch path
**Gap**: The verification check is disabled by `if (false)`, so no test can currently catch a `bytes_total` vs. accumulated block size mismatch. The model-test-long-random-config-disagg test (WT-16864) exercises the general path but hits an unrelated page ID mismatch failure. No targeted unit test for the accounting leak exists.
