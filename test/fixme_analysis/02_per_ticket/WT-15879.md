## What this FIXME asks for
In disaggregated storage, after a successful checkpoint, old checkpoint root pages that are marked for deletion are freed by calling `bm->free()` directly from `checkpoint_txn.c` inside `__checkpoint_tree`. This is done after `checkpoint_resolve` to ensure the new checkpoint is durable before removing the old root page. However, this discard call is made from the checkpoint layer rather than from within the disaggregated block manager layer, creating a layering violation. The FIXME asks that the discard logic be moved into the block manager (either into an existing function or a new dedicated function), to keep disagg-specific block management decisions within the block manager layer. This depends on a related design decision tracked in WT-15861.

## Importance: MEDIUM
**Reasoning**: The current code works correctly in practice — the root page is freed at the right time (post-resolve) — but the layering violation makes the code fragile: if the checkpoint resolution sequence changes, the discard call could be placed incorrectly. Keeping disagg-specific block operations inside the block manager layer is important for maintainability and for correctness if the checkpoint flow is refactored.

## Test Coverage: PARTIAL
**Relevant tests**: test/format (disagg modes), test/suite/test_layered*.py
**Gap**: The discard of old checkpoint root pages is exercised by any disagg checkpoint cycle, so the functional behavior is tested. However, there is no test that verifies the discard is performed within the correct layer or that validates the layering boundary. The structural improvement (moving the call) would be validated only by code review.
