## What this FIXME asks for
The `__wt_atomic_stats_max_*` and `__wt_atomic_stats_min_*` inline functions use a non-atomic load-compare-store pattern: they load the current value with a relaxed atomic load, compare it to the new value, and if greater/lesser perform a relaxed atomic store. This is a classic TOCTOU race — two threads may both observe the old value, both decide to update, and only one write actually represents the true maximum. The FIXME proposes replacing the load+store with a relaxed CAS loop so that no update is silently lost, making the max/min statistics lossless under concurrent access. Performance measurements are needed before committing to the change.

## Importance: LOW
**Reasoning**: LOW. Max/min statistics are inherently advisory and losing an occasional update is acceptable for performance counters (e.g., max eviction queue depth). However, if any max/min stat is used in correctness decisions or capacity planning, the loss could be misleading. The fix is straightforward and the CAS loop is still cheap for lightly-contended stats.

## Test Coverage: UNCOVERED
**Relevant tests**: none found specifically exercising concurrent max/min stat updates to catch lost writes; the functions are called transitively in many tests but races are not detectable without specific concurrency stress.
**Gap**: No test deliberately runs two threads racing to update the same max/min stat and verifies the final value is the true maximum, so the load+store race would not be caught even in TSAN-enabled runs (TSAN may not flag relaxed-atomic load+store as a race).
