## What this FIXME asks for
On a follower node, when a layered cursor is positioned on the stable cursor, the code currently refuses to advance to a newer checkpoint to avoid losing the cursor position. The FIXME notes that if timestamped reads are in use and the invariant is guaranteed that no checkpoint with an oldest timestamp newer than the pinned timestamp is ever installed, it would be safe to advance to a newer checkpoint (the desired version would still be readable). This optimization is blocked on the broader guarantee tracked in WT-16467: that the follower panics rather than installing a checkpoint whose oldest timestamp exceeds the pinned timestamp, thereby making that guarantee safe to rely on.

## Importance: HIGH
**Reasoning**: The inability to advance stable cursor checkpoints during a positioned timestamped read limits read freshness on follower nodes. More critically, without the panic guardrail (WT-16467), a follower can silently install a checkpoint that makes historical data unreachable, causing incorrect reads — a correctness risk. The Jira ticket is actively being worked (Blocked on SERVER-123308) and has linked BF score of 200.
