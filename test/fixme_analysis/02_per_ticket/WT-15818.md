## What this FIXME asks for
When the disaggregated block manager detects that a requested page LSN is ahead of the materialization frontier (the point up to which page-log data has been materialized locally), it currently emits only a warning and increments a statistic (`disagg_block_read_ahead_frontier`). The FIXME asks whether this condition should cause a crash (panic/assert) instead. The Jira ticket lists four blocking issues: (1) the frontier is not known immediately at step-up so reads before it is set would false-positive, (2) the Server sends magic LSN values that confuse the check, (3) it is unconfirmed whether the frontier is correctly updated on secondary nodes, and (4) a test-vs-production distinction is needed so crashing is enabled only during testing. A recent BF (BF-41481) confirmed we are still not ready to enable crashing.

## Importance: MEDIUM
**Reasoning**: Reading a page whose LSN is ahead of the materialization frontier can silently return stale or incorrect data, which is a correctness concern in disaggregated storage. The current warning-only behavior means such events may go unnoticed in production. However, since several pre-conditions must be resolved first (magic LSNs, step-up races, secondary updates), turning this into a hard crash prematurely would cause spurious crashes.

Tests observing `disagg_block_read_ahead_frontier` could detect violations but are not currently present.
