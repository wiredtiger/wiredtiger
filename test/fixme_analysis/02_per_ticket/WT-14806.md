## What this FIXME asks for
The layered cursor implementation uses an in-band tombstone marker (`"\x14\x14"`, two DC4 bytes) stored directly in the value to indicate deleted records. The comment claims that if an application coincidentally uses this same two-byte sequence as a value, the only consequence is a wasted copy — but Jira discussion has flagged this as potentially incorrect or understated. The FIXME asks for: (1) tests verifying the claimed collision behavior, (2) clarification of why the in-band tombstone is needed rather than an out-of-band signal, and (3) investigation of possible data corruption if `__clayered_modify()` produces a value starting with the tombstone marker.

## Importance: HIGH
**Reasoning**: This is a potential correctness bug. If an application stores a value beginning with `"\x14\x14"`, the layered cursor's delete detection code (`__wt_clayered_deleted`) would misinterpret it as a tombstone and return WT_NOTFOUND, causing silent data loss from the application's perspective. The `__clayered_modify()` path is specifically called out as potentially generating tombstone-colliding values through accumulated modifications. A reviewer (Yury Ershov) confirmed this as requiring additional research and possible data corruption in the modify path. Rated P3/Major in Jira.
