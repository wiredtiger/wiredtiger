## What this FIXME asks for
Multiple places in the connection startup and btree-open paths need to determine early whether the engine is running in disaggregated mode. The proper API (`__wt_conn_is_disagg`) is only available after metadata recovery has run. As a result, several startup functions resort to inspecting the raw config string for `disaggregated.page_log` rather than calling the proper function, and `bt_handle.c` uses a URI file-extension string check to detect disaggregated btrees. The FIXME asks for a single, reliable early-startup disagg flag that can be set before metadata recovery, eliminating all these scattered hacks.

Additionally, `conn_api.c:3450` captures a dependent follow-on: once the proper detection is in place, precise checkpointing should be automatically enabled for disagg connections without requiring explicit MongoDB-side configuration.

## Importance: MEDIUM
**Reasoning**: The scattered config hacks are fragile — a config-string rename or new disagg mode could silently disable all these early checks without compiler errors. The URI extension check in `bt_handle.c` is particularly brittle. A regression here could cause disagg-specific code paths (tiered storage suppression, precise-checkpoint enablement, startup directory cleaning, byte-locking) to be silently skipped, leading to incorrect behaviour in disaggregated deployments.
