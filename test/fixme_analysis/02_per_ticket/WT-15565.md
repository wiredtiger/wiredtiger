## What this FIXME asks for
When `precise_checkpoint` and `ops.prepare` are both enabled in the test/format stress test, the `ops.truncate` operation is forcibly disabled because prepared fast truncate cannot yet be written to disk. The FIXME tracks the missing implementation: encoding prepared transaction IDs into disk records for fast truncate operations, analogous to what already exists for normal (non-truncate) prepared operations. Until this is implemented, the test configuration silently suppresses truncate testing whenever prepared transactions and precise checkpoints are combined.

## Importance: MEDIUM
**Reasoning**: MEDIUM. The gap is functional — a combination of features (prepared transactions + precise checkpoint + truncate) is untested and unsupported. It will become HIGH if prepared transactions and disaggregated storage both reach GA with truncate workloads, as data loss during recovery is possible if a prepared truncate is not durably recorded.

## Test Coverage: UNCOVERED
**Relevant tests**: test/format/format_config.c (the workaround itself is in the stress test), test/format/ (format stress test suite)
**Gap**: The truncate+prepare+precise_checkpoint combination is entirely suppressed by `config_off(NULL, "ops.truncate")` when those flags are set — no test exercises the missing code path. There is no standalone test for prepared fast truncate durability.
