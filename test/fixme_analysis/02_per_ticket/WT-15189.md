## What this FIXME asks for
The `clayered_next_random` implementation propagates `next_random=true` from the layered cursor down onto the constituent ingest cursor. When the deletion-skip loop in `__clayered_iterate` calls `constituent->next()` to advance past magic-byte tombstones, it invokes the random-pick implementation instead of a sequential advance. If every row in the ingest B-tree's picker range is tombstoned, every "skip" draws another random tombstoned row and the loop spins indefinitely. The FIXMEs ask for a correct implementation of random-cursor traversal on layered tables so that `ops.random_cursor` can be re-enabled in the format stress test and `test_layered_fast_truncate05` can be unskipped.

## Importance: HIGH
**Reasoning**: This is an active CI blocker (tagged `Disagg CI-blocker`) with 17+ failing build variants as of the ticket description and 4 linked BFGs in the last 30 days. The test is completely skipped (`@unittest.skip`), meaning an entire class of cursor behavior (random reads over fast-truncated ranges on follower nodes) is untested. The root cause — random picks being used for sequential skip — is a semantic correctness bug, not merely a test gap.
