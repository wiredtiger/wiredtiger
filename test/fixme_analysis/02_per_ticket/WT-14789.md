## What this FIXME asks for
After the layered tables merge, `CURSOR_API_CALL` was changed to take a `dhandle` argument instead of a `btree` argument. In several call sites where a dhandle is not always available (e.g., when `incr_cursor` is NULL in the incremental backup cursor), callers now use awkward ternary expressions like `btree == NULL ? NULL : ...` to pass NULL safely. The FIXME requests a cleaner API — perhaps a new helper macro or wrapper (e.g., `CURSOR_API_CALL_SESSION_DH`) that handles the NULL case without requiring every caller to duplicate defensive NULL checks.

## Importance: LOW
**Reasoning**: This is a code quality and maintainability issue, not a correctness bug. The NULL check works correctly as written. However, the proliferation of this pattern across the codebase (the Jira description notes "a bunch of code" does this) increases cognitive overhead and the chance that a future caller forgets the NULL guard. Rated P3/Major in Jira but the actual risk is low since it is purely cosmetic.
