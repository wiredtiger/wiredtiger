## What this FIXME asks for
When `cursor->modify()` is called with a read timestamp between a tombstone (removal at T2) and a subsequent re-insert (T3), and the in-memory update chain has been cleared (e.g. after checkpoint), WiredTiger returns `WT_NOTFOUND` instead of `WT_ROLLBACK`. The correct behavior is to detect the invisible committed re-insert at T3 and return `WT_ROLLBACK` so the caller can retry with a higher read timestamp. The FIXME is a workaround in `test/format`: predictable replay mode now explicitly checks `replay_stale_read_ts()` and forces a rollback before calling modify, bypassing the kernel bug. The FIXME asks that this workaround be removed once the underlying engine bug is fixed.

## Importance: HIGH
**Reasoning**: This is a correctness bug with data corruption potential. `WT_NOTFOUND` from modify is treated as a silent no-op by callers — a write transaction can silently drop a modification that should have been applied or retried. In a MongoDB workload that mixes reads and writes in the same transaction across a key that was deleted and re-inserted within the transaction's timestamp window, the modify is silently lost. This is the same class of bug as WT-17247 (remove returning WT_NOTFOUND instead of WT_ROLLBACK). The workaround in test/format prevents the test from exposing the bug but does not fix it in production.

## Test Coverage: PARTIAL
**Relevant tests**: test/format/ops.c (predictable replay mode); no direct regression test for the specific tombstone scenario
**Gap**: The `replay_stale_read_ts()` guard prevents the test from hitting the bug. Once the engine fix lands, the guard must be removed and the test must verify that modify correctly returns `WT_ROLLBACK` in the outdated-tombstone scenario. A targeted unit or integration test for the tombstone/re-insert/modify sequence is also missing.
