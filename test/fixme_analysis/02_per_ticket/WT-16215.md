- **Priority**: Major - P3

## What this FIXME asks for
`__wt_meta_track_init` is called after `__wt_txn_recover` completes during connection open. However, `__wt_txn_recover` calls `__schema_drop`, which in turn calls `__wt_meta_track_off` — invoking meta-tracking infrastructure before it has been initialized. The current workaround gates the sync call on `need_sync`, skipping it during recovery and partial-backup-restore. The FIXME asks for a proper investigation into whether meta tracking is genuinely needed during recovery, and if not, for a clean solution that prevents it from being called in uninitialized state.

## Importance: HIGH
**Reasoning**: Calling `__wt_meta_track_off` against uninitialized meta-tracking state is a latent use-before-init bug. Even though the current flag-based guard prevents the dangerous sync call, it leaves the meta-tracking subsystem in an undefined state during the call. If the guard is ever incorrect, removed, or the call path changes, this could result in a crash or silent metadata corruption during recovery — at the worst possible time (database startup after a crash).

## Test Coverage: PARTIAL
**Relevant tests**: test/suite/test_txn_recover*.py; partial-backup-restore tests
**Gap**: No test specifically validates that meta tracking is not called during recovery, nor verifies that the `need_sync` guard is correct for all recovery paths (recovery, partial backup restore). The condition relies on two connection flags being set correctly; there are no tests for the case where those flags might be absent during a recovery-adjacent code path.
