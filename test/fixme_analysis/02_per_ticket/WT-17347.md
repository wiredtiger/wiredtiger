## What this FIXME asks for
When committing a fast truncate transaction, `__wti_mark_committed_truncate_table_apply` acquires a queue-wide write lock (`truncate_lock`) to update the `txn_id`, `start_ts`, and `durable_ts` fields of the truncate entry. This is overly broad — locking the entire truncate queue for a three-field update on a single entry serializes all concurrent readers that need to check truncate visibility. The FIXME asks to replace this with a per-entry publish state (following the same pattern as `__txn_apply_prepare_state_update` for prepared updates), using acquire/release atomic writes to provide per-entry consistency without holding the queue-wide lock during commit.

## Importance: MEDIUM
**Reasoning**: This is a performance issue rather than a correctness bug. The queue-wide write lock on commit creates contention between the committing transaction and any concurrent readers scanning the truncate list for visibility. In workloads with many concurrent fast truncates this lock could become a bottleneck. The fix (per-entry state with atomics) is actively in code review and would align the truncate commit path with the established pattern for prepared updates. The current behavior is correct.
