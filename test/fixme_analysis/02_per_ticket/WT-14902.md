## What this FIXME asks for
Precise checkpoint mode (`WT_CONN_PRECISE_CHECKPOINT`) currently can only be set at connection open time. If it were made reconfigurable at runtime, enabling it mid-session could leave the database in an inconsistent state: pages previously reconciled without the precise-checkpoint constraint (i.e., with updates beyond the stable timestamp written to disk) would be incompatible with the stricter visibility rules. The fix requires running Rollback to Stable (RTS) before the first precise-mode checkpoint to clean up any over-stable data that may already be on disk.

## Importance: HIGH
**Reasoning**: This is a correctness constraint, not just a quality-of-life item. If precise checkpoint mode is ever enabled via reconfiguration without first running RTS, the checkpoint could include data beyond the stable timestamp, violating the precise-checkpoint invariant. For disaggregated storage, which relies on precise checkpoints for correctness of the standby replication path, this would produce an incorrect checkpoint that could corrupt the replica's view of the data.
