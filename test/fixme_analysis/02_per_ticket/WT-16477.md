## What this FIXME asks for
When opening a stable btree dhandle on a follower/standby node, the current code takes a global checkpoint lock to ensure consistent checkpoint metadata is read for both the data store and history store. This lock is expensive and can cause stalls, especially for databases with many tables. The FIXME asks for a direct read from the shared metadata table (bypassing local metadata), which would provide consistency without requiring the checkpoint lock. The second occurrence in `session_dhandle.c` is a workaround that enforces a fixed lock ordering (checkpoint before schema) to prevent deadlocks, which also would be unnecessary after the shared-metadata approach is implemented.

## Importance: MEDIUM
**Reasoning**: The current workaround is functionally correct but introduces a performance bottleneck in disagg follower workloads with many tables. The lock ordering workaround in session_dhandle.c adds complexity and code fragility. While not a correctness risk today, the scalability issue could become significant as disagg adoption grows.
