## What this FIXME asks for
The `__cursor_page_pinned` function skips the fast-path cursor optimization for any search operation running at read-committed isolation. The two code paths (fast-path using a pinned page vs. full B-tree search) consult transaction IDs differently, and at read-committed isolation this produces inconsistent search results depending on where the cursor started. The FIXME asks for the fast path to be corrected so it can be used safely at read-committed isolation, eliminating a per-search performance penalty for read-committed workloads.

## Importance: MEDIUM
**Reasoning**: The current guard is a correctness workaround — bypassing the fast path means results are correct but at the cost of forcing a full B-tree traversal on every search under read-committed isolation. If the guard were removed without fixing the underlying transaction-ID handling divergence, read operations could return stale or incorrect visible values (wrong results). As a performance regression it affects all read-committed search/search-near callers, which is a commonly used isolation level in MongoDB.
