## What this FIXME asks for
TSAN does not support standalone memory fences (full barriers), causing false-positive data-race warnings. As a workaround, the log manager's `log_close_fh` store was weakened from a `WT_FULL_BARRIER` + relaxed store to a release-semantic atomic store, but only under the `TSAN_BUILD` compile macro. The comment and associated reasoning state that release semantics are actually sufficient here because `log_close_fh` being set to NULL is the publication event that makes `log_close_lsn` visible to `__log_newfile`. The FIXME asks for a formal decision on whether the weakened (release) form is correct enough to use in production builds unconditionally, eliminating the `WT_FULL_BARRIER` and the `#ifdef TSAN_BUILD` guard.

## Importance: MEDIUM
**Reasoning**: The production path currently uses a `WT_FULL_BARRIER` which is stronger than necessary (per the code comment), meaning there is no correctness risk in the current code. However, keeping the TSAN and non-TSAN paths divergent means TSAN testing does not validate the exact barrier ordering used in production. If the analysis in the comment is wrong and release semantics are insufficient, TSAN builds could silently pass while production builds have a race. The ticket is in the unassigned backlog with no recent activity.

## Test Coverage: PARTIAL
**Relevant tests**: Log-manager tests in `test/suite/` (e.g. `test_log*.py`) exercise the log-file rotation path; TSAN CI variants run with the weakened barrier.
**Gap**: There is no targeted test that validates the memory-ordering contract between `log_close_fh`, `log_close_lsn`, and `__log_newfile`. The divergence between TSAN and production builds means the ordering proven safe by TSAN is not the ordering actually used in production.
