## What this FIXME asks for
The reconciliation timing code asserts that total reconciliation time (`rec`) is less than one day in milliseconds, but does not apply a similar upper-bound sanity check to the two sub-timings: `rec_hs_wrapup` (history store wrapup phase) and `rec_img_build` (page image build phase). The FIXME asks for assertions to be added for those two sub-timings as well, to catch any overflow or instrumentation bug.

## Importance: LOW
**Reasoning**: This is a defensive assertion gap. Without the assertions, a badly overflowed or incorrectly computed sub-timing would be silently recorded into `conn->rec_maximum_hs_wrapup_milliseconds` and `conn->rec_maximum_image_build_milliseconds` statistics, potentially producing misleading performance data. There is no correctness risk to data, only to diagnostic accuracy.

## Test Coverage: UNCOVERED
**Relevant tests**: none found
**Gap**: No test validates the upper-bound sanity of reconciliation sub-timing values. The existing assertion only covers the total reconcile time, leaving the two sub-stage timers unguarded.
