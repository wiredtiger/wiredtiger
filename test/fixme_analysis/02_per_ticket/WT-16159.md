## What this FIXME asks for
PALite (the lightweight single-process SQLite-backed page-log backend used for testing) currently does not support concurrent access by multiple processes. When two processes of `test/format` run simultaneously against the same storage directory (as needed for leader-follower switch-mode tests), SQLite serializes writes and can return `SQLITE_BUSY` or `SQLITE_LOCKED`. The workaround in `configure()` retries for up to 60 seconds with 100 ms intervals. The FIXME asks for a proper inter-process synchronization mechanism in PALite so that only one writer is active at a time and others block rather than fail.

## Importance: MEDIUM
**Reasoning**: The retry-loop workaround may mask real contention bugs and does not guarantee forward progress if contention is sustained beyond 60 seconds. More importantly, without true multi-process support, disaggregated-storage leader-follower switch tests cannot reliably run concurrently, which limits the test coverage of switch-mode scenarios. However, PALite is a testing-only backend, so the impact is confined to test infrastructure quality rather than production correctness.

## Test Coverage: PARTIAL
**Relevant tests**: test/format (uses PALite in switch-mode), ext/page_log/palite/
**Gap**: No tests specifically validate that concurrent multi-process PALite access is handled correctly (only-one-writer semantics, no SQLITE_BUSY failures under sustained concurrency). The retry workaround papers over the gap but does not test the desired behavior.
