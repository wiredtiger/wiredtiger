## What this FIXME asks for
The materialization frontier LSN check in `__block_disagg_check_lsn_frontier` skips its check when `last_materialized_lsn` equals `WT_DISAGG_START_LSN` (defined as `(uint64_t)1 << 32` = 4294967296). This magic value is injected by the MongoDB Server when stepping up a node, as a sentinel meaning "not yet valid." WT-15872 introduced this workaround to stop false positive "LSN frontier violation" warnings during step-up; WT-15914 asks that the root cause be resolved — ideally by eliminating the magic constant entirely, or by establishing a clean protocol with the Server that does not rely on a sentinel value in the middle of the valid LSN space.

## Importance: HIGH
**Reasoning**: The magic constant `WT_DISAGG_START_LSN` silently disables the materialization frontier check during the entire step-up window. If the Server inadvertently sets this value outside of a step-up, or if WiredTiger reads it as a real LSN, the frontier check provides no protection. The current workaround also links WiredTiger's internal invariant enforcement to a Server-side convention (defined in `wiredtiger.h.in`) that is fragile and opaque. Resolving this properly is a prerequisite for WT-15818 (making the frontier violation a hard crash).
