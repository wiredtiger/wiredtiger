## What this FIXME asks for
Inside `__wti_log_release()`, the code reads `log->sync_lsn.l.file` (a 32-bit field within a 64-bit atomic LSN struct) without holding the `log_sync_lock`. Concurrently, the log-close server thread performs a 64-bit atomic write to the full `log->sync_lsn` via `__wt_atomic_store64`. TSAN reports this as a data race because the 32-bit sub-field read overlaps with the 64-bit atomic write at the same address. The workaround uses `__wt_tsan_suppress_load_uint32()` to silence TSAN. The FIXME asks for proper synchronization — either holding the lock around the read, using a full 64-bit atomic load, or restructuring the code so the sub-field is not accessed outside the lock.

## Importance: HIGH
**Reasoning**: HIGH. This is an active, confirmed data race in the WAL release hot path. While the current behavior may be benign on most architectures (the read observes a slightly stale file number), it is undefined behavior under the C memory model and a latent crash/corruption risk on architectures with non-atomic sub-word accesses. The TSAN suppression hides the warning rather than fixing the underlying race.

## Test Coverage: PARTIAL
**Relevant tests**: Any test that runs with TSAN and exercises concurrent logging will trigger this — the original report came from `ex_backup` with TSAN. Standard Python test suite exercises log release but TSAN suppression masks the warning.
**Gap**: No test validates that `log->sync_lsn` is accessed safely under the required lock; the suppression macro means TSAN-enabled CI passes without diagnosing the race.
