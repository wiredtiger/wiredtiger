## What this FIXME asks for
After a `search_near` call, `clayered->current_cursor` can be NULL when the operation returns `WT_NOT_FOUND` or encounters an error. The code that increments per-cursor ingest/stable statistics compares `current_cursor` against `ingest_cursor` without first checking for NULL, which means the increment goes to the `else` (stable) branch instead of neither branch when no row is found. The FIXME asks for a NULL guard before the comparison so that ingest/stable statistics are only incremented when a valid result cursor is set.

## Importance: LOW
**Reasoning**: This is a statistics accuracy bug, not a correctness or crash bug. An unchecked NULL dereference is not present here because the comparison `clayered->current_cursor == clayered->ingest_cursor` is a pointer equality check that is safe when `current_cursor` is NULL — it will simply be unequal to `ingest_cursor` and increment the stable counter erroneously. The inaccuracy inflates `layered_curs_search_near_stable` counts by the number of not-found search_near calls, which could mislead performance analysis but does not affect data integrity.

## Test Coverage: UNCOVERED
**Relevant tests**: `test/suite/` layered cursor tests exercise `search_near` on layered tables.
**Gap**: No existing test validates the values of `layered_curs_search_near_ingest` or `layered_curs_search_near_stable` statistics, particularly in the NOT_FOUND case. A targeted test asserting that neither counter is incremented when `search_near` returns `WT_NOT_FOUND` would catch this regression.
