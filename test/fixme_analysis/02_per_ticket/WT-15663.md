## What this FIXME asks for
The block cache has a correctness bug: when a page is returned from the cache without compression or encryption (`!expect_conversion`), a buffer copy is attempted via `__wt_buf_set()`, but if the input pointer `ip` equals the output `buf` the copy is a no-op and the caller receives a direct reference into the live cache entry. This means the caller can modify or observe stale cache content. Until this is fixed, the block cache is entirely disabled at runtime (any `block_cache.enabled=true` config is silently ignored with a warning), and the layered/disaggregated test `test_layered43` is permanently skipped.

## Importance: HIGH
**Reasoning**: HIGH. The root bug is a data-aliasing correctness issue — callers receiving a live cache pointer instead of a copy can corrupt or incorrectly read block cache data. The full block-cache feature is disabled as a consequence, so all users expecting a performance benefit from block caching are silently getting none. Re-enabling block cache requires fixing this bug first.
