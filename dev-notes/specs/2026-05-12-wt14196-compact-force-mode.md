# WT-14196 Compact `force` Mode

**Date:** 2026-05-12
**Branch:** `sean-compact-perf`

## Motivation

While running the `compact-stress.wtperf` benchmark with verbose `compact:2`
logging enabled, we observed that under concurrent update load
`session->compact()` returned after a single useful pass, with the second
pass bailing out via:

```
file:test.wt: skipping because the file has grown between compact passes.
```

The result on the 5-minute canonical run: **5 pages rewritten**, file size
**grew** by ~950MB (3.6GB → 4.5GB). Compact was correctly detecting that the
update workload was outpacing it and giving up, which is the conservative
behaviour but masks any signal about *how well compact would do if it kept
trying*.

A quick experiment removing the file-grew check entirely (no-bail-out hack)
on the same 5-minute workload produced **11 compact passes** and
**55,627 pages rewritten** — three orders of magnitude more work. The
workload exhibits the WT-14196 pathology much more strongly when compact is
allowed to continue.

To support both the production-safe default and the "keep trying" mode
required for benchmarking and pathology investigation, a new `force`
configuration option was added to `WT_SESSION.compact`.

## API

```c
session->compact(session, "table:foo", "force=true");
```

CLI:

```
wt compact -c "force=true" table:foo
```

Default is `false`, preserving existing behaviour.

## Bail-outs overridden by `force=true`

| Bail-out | Location | Force overrides? | Rationale |
|---|---|---|---|
| File grew between passes | `block_compact.c:__wt_block_compact_skip` | **Yes** | Primary motivation |
| Avail < `free_space_target` on first iter | `block_compact.c:__wt_block_compact_skip` | **Yes** | Heuristic, parallel knob to `free_space_target` |
| <10% avail in first 90% of file | `block_compact.c:__block_compact_skip_internal` | **Yes** | Heuristic; force defaults to last-20% target |
| No new pages rewritten on prev pass | `block_compact.c:__block_compact_skip_internal` | **Yes** | Stall detector; force retries |
| File ≤ 1MB | `block_compact.c:__wt_block_compact_skip` | **No** | Hard physical limit (compact needs end-of-file headroom to move blocks) |
| Per-page wouldn't shrink file | `block_compact.c:__compact_page_skip` | **No** | Overriding would change semantics from "compact" to "rewrite all pages" |
| `timeout` max_time elapsed | `session_compact.c` | **No** | Separate explicit user knob |

When force=true, the verbose `WT_VERB_COMPACT` logs explicitly note when the
override fires (e.g. `"file has grown between compact passes, continuing
because force=true"`) so a reader of a compact log can see exactly which
heuristic was bypassed.

## Follow-ups (not done here)

- Plumb a `compact_config` (or similar) option through wtperf's
  `compact_worker` so the canonical `compact-stress.wtperf` runner can set
  `force=true`. Today `compact_worker` calls
  `session->compact(session, uri, NULL)` unconditionally.
- Fix the wtperf-level race observed in the no-bail-out experiment: when
  `run_time` elapses while compact is still inside `session->compact()`,
  `compact_summary.txt` is written with stale (zero) post-compact stats and
  a uint64 underflow in `Update ops during compact`. The fix is to either
  capture post-stats from inside the compact_worker after `session->compact`
  returns regardless of `wtperf->stop`, or to disable the `run_time`
  override when `compact_ends_workload=true`.
- Once the wtperf plumbing exists, run baseline (default) vs treatment
  (force=true) on the canonical config and record the results next to
  `2026-05-11-wt14196-baseline-results.md`.
